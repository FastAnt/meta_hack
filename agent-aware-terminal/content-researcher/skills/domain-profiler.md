# Skill: domain profiler

Goal: know what this project *is* and what the user *just
asked for*, precisely enough to pick one great content idea.

1. Start from `.aat/research/domain_profile.json` (deterministic
   keyword profile: domains, scores, evidence, angles).
2. Verify against reality — read the project README and 3–5
   representative source files. Keyword counts lie; a folder
   named `audio/` full of UI code is a UI project.
3. Weight the latest user task above everything: it names the
   subdomain in play *now* (e.g. "spectrogram denoising" inside
   a general audio app → spectrograms, not amplifiers).
4. Produce, in your head or in the report:
   - primary domain + subdomain,
   - 3 concrete concepts a practitioner would enjoy being
     quizzed on (mechanisms, not vocabulary),
   - 1 surprising-but-true fact candidate.
5. Prefer mechanisms over definitions. "Which band survives a
   low-pass at 8 kHz?" beats "What is a filter?". Definition
   recall is filler; use it only when nothing better exists.
